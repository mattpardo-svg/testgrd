Overall: The alternative delivers the core calculation: hourly, updated D+1 security analysis from the evening of D. It does not deliver what the CR calls “the expected significant change”, which is extending all IDCF functions from 24H to 30H. D and D+1 stay two separate 24H business days everywhere: GUI, DDP and reports. The vendor’s own Motivation reframes the requirement, so the TSOs must explicitly accept this reinterpretation.

Coverage per CR chapter

2.1 Timing ⚠️
Covered: a parallel D+1 intraday run at configured times.
Not specified: the configured hours and the scheduler parameters.
❌ The “24 → 29/30 timestamps” requirement is explicitly not done.
❌ Using DACF remedial actions (topological measures) in the D+1 run is not addressed.
2.2 Input model monitoring ⚠️
Map, Table and Vulcanus get a new date selector, so D and D+1 are viewed separately rather than as 30H.
X-node GUIs are unchanged.
D+1 IGM validation and validation messages to TSOs/TSCNET are implied by “standard input processing” but not stated.
2.3 Vulcanus ⚠️ Separate D and D+1 views. The SD does not state that intraday Vulcanus for D+1 is stored separately from DACF Vulcanus with no overwrite.
2.4 Merge / LF / CA ⚠️
Runs automatically; standard merge, LF and CA; ECs and Automatics included.
Substitution is the “standard” one, not the CR’s “initial DACF dataset for non-participating TSOs”. Needs confirmation of what standard substitution does for a future business date with no prior IDCF versions.
2.5 Change Manager & Model improvements ❌ The DDP stays at 24H per day and must be opened separately for D and D+1. Transferring DACF remedial actions to the extended IDCF is not addressed.
2.6 Automatics & ECs ✅ Standard configuration.
2.7 PST configuration ⚠️ Standard config, so D+1 uses the same hourly settings. There are no D+1-specific options, same as chapter 5.
2.8 Visualization ❌
All results screens stay at 24H per selected date.
No 29H Security Monitor, Security Results Overview, Trend Analysis or Multi-tab view.
No Compute-All across both days.
2.9 Reporting ❌ Separate reports per business date in separate folders. That matches neither Option 1 (one sheet) nor Option 2 (two sheets in one report).

What it adds that the CR doesn’t ask for

Business date in message subjects.
Date selector on the overview page.
A second progress bar for the parallel process.

Open points / risks

Two intraday processes run in parallel at HH:15. Performance and completion time are not addressed.
Continuity at 00:15 is not addressed: how D+1 cycles and versions carry over when D+1 becomes D.
Figure 19: both progress bars show the same date (19.10.2026), so the mockup looks wrong or is unclear.
It is unclear whether the manual Intraday trigger can start a D+1 run.

Verdict: About half of the CR is met, mainly the calculation side (2.1 partly, 2.4, 2.6, 2.7). The integrated 30H view (2.2, 2.3, 2.5, 2.8, 2.9) is not delivered. This is a TSO decision: lower effort versus losing the “bridge the gap” view.
